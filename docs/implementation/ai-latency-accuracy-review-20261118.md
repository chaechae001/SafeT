- 작성일: 2026-11-18 (Asia/Seoul)
- 상태: 팀 공유용 제안. 모델·서버 자원·출력 계약 변경은 미확정.
- 검토 기준: main 커밋 `7514acd92b7d46864bb274d005a3844f83c1e60c`.
- 범위: 저장소 코드와 기존 실험 기록 검토. 이번 검토에서 실제 모델 호출·GPU 측정·학습은 하지 않았다.
- 사용자 체감 40~50초는 문제 제보이며, 아래 실험 수치와 동일한 조건의 측정값으로 간주하지 않는다.

## 핵심 판단

사진 처리에서는 모델 교체·로딩 제거가 가장 먼저 검증할 속도 개선 후보다. 키워드 선표시와 상세 분석 분리로 첫 결과까지의 시간을 줄일 수 있다. 정확도 향상은 별도로 현장 라벨 검수, 기기명 정규화, 혼동 사례 학습과 검증이 필요하다. 개선 후 시간을 아직 보장할 수 없다.

## 확인된 구조와 수치

약 9.7GB GPU에서 평소 EXAONE·STT를 유지하고, 사진 입력 시 둘을 내린 뒤 SAM 3를 실행하는 구조가 기록돼 있다.

| 단계 | 기존 측정 |
|---|---:|
| LLM·STT 내림 | 2.4초 |
| SAM 3 프로세스 시작·로딩·탐지 | 49.3초 |
| 사진 도착 → 기기 확인 화면 | 52.5초 |
| 확인 화면 이후 LLM·STT 재적재 | 추가 41.0초 |

별도 탐지 비교 실험의 SAM 3 사진당 평균은 로딩 제외 4.61초, 모델 로딩은 19.1초다. 실험 조건이 다르므로 위 시간과 단순 차감해 개선량을 계산하지 않는다.

관문 연결 기록에는 합성 사진 탐지 약 41.7초와 토큰 계수 경로 미지원이 기록돼 있다. 이는 당시 상태이며 현재 서버 상태를 새로 확인한 결과가 아니다. 실제 서비스 코드의 사진 → 토큰 계수 → 생성 경로와 실험용 확인 화면 흐름도 구분해야 한다.

## 제안 1: 모델 교체 비용 줄이기

자원 확대가 가능하면 SAM 3와 EXAONE·STT를 GPU별로 분리하거나 동시 상주 가능한 환경을 검증한다. 시작 시 로딩·워밍업을 끝내고 요청마다 프로세스를 재시작하지 않는 방향이다. 모델을 유지하므로 정확도 저하 없이 속도를 개선할 우선 후보다. 동시 상주 가능 여부는 가중치뿐 아니라 KV 캐시·추론 피크·동시 요청을 포함해 측정한다.

현재 GPU를 유지한다면 프로세스·CPU 메모리 유지와 GPU 적재 전환 방식의 비용을 비교한다. 요청 묶음 처리도 교체 횟수를 줄일 수 있지만 개별 요청의 대기 시간을 늘릴 수 있다. 검증 없이 현재 GPU에 모든 모델을 동시에 올리지 않는다.

## 제안 2: 키워드와 상세 분석 분리

현재 서비스는 기기명 외에 카탈로그 후보 ID, 이유, 근거, 확인 질문을 생성한다. 키워드 표시가 목표라면 상세 분석 완료를 기다리는 구조를 분리하는 방안을 검토한다.

```text
사진 → 기기 탐지 ─────────────→ 기기 후보 선표시
텍스트 → 기기·작업명 매칭 ────→ 키워드 선표시
음성 → 전사 → 기기·작업명 매칭 → 키워드 선표시
                                  ↓
                         카탈로그 후보 검색
                                  ↓
                       LLM 문맥·근거·질문 분석
```

- 튀김기·프라이어·후라이어 등 별칭을 기기 ID로 정규화한다.
- 기기의 존재, 실제 사용, 노출, 부정 표현을 분리한다. “튀김기는 있지만 사용하지 않는다”를 작업 수행으로 확정하지 않는다.
- 선표시 결과는 잠정 후보임을 표시하고 상세 분석과 혼동하지 않게 한다.
- 실험 그래프의 text_to_equipment·별칭 매칭을 재사용 후보로 검토하되 서비스 계약에 맞춰 별도 검증한다.
- 첫 후보 표시 시간과 전체 분석 완료 시간을 각각 측정한다. 선표시만으로 전체 연산 시간이 줄었다고 보고하지 않는다.

## 제안 3: 사진 탐지의 도메인 적합성 개선

내부 비교 F1은 SAM 3 0.53, YOLOv8x-World 0.30이었다. 무학습 YOLO 교체는 속도와 정확도를 함께 개선한다고 볼 수 없다.

중기 후보는 사람 검수 라벨로 학습한 경량 기기 탐지기다. 가스레인지·그릴·철판, 작업대·싱크 등 혼동 사례를 포함한다. 경량 탐지 후 불확실·입력 불일치 사례를 SAM 3로 재검토하는 방식도 비교한다. 다만 높은 점수의 오탐과 미탐도 있으므로 낮은 점수만 재검토 기준으로 삼지 않는다.

단기 후보는 SAM 3의 사진당 39개 프롬프트를 업종·입력에 따라 우선순위화하는 것이다. 예상 밖 기기를 놓치지 않도록 추가 탐색 경로와 재현율 검증을 둔다. 현재 비교 코드는 사진당 set_image를 한 번 호출하므로 이미지 인코딩 재사용을 새 개선으로 중복 제안하지 않는다.

현재 34장 평가는 AI 보조 라벨·사람 검수 전·치킨 매장 위주다. 같은 평가셋으로 임계값을 선택한 한계가 있다. 매장·장면 단위로 학습/검증/최종 평가를 분리하고 새로운 업종을 포함한다. 현재 기본 임계값 0.35는 유지하며, 이 문서는 새 임계값을 결정하지 않는다.

## 제안 4: LLM 출력과 반복 입력 비용 줄이기

현재 적용된 사진 결과 캐시, 기기별 최고 점수 요약, temperature=0, JSON 출력 요청은 유지한다.

추가 검토:
- 키워드 단계는 필요한 ID·직접 근거 중심으로 출력한다. 상세 설명은 필요한 단계에서 생성한다.
- 배포 버전이 지원하는 JSON Schema·허용 ID enum 제약으로 형식 오류를 줄인다. 형식 준수는 사실 정확성을 보장하지 않는다.
- 고정 지침·카탈로그에 prefix caching 적용 여부를 확인한다. 반복 입력 처리에 효과가 있으며 출력 생성 자체는 빨라지지 않는다. 모델 재시작 시 캐시 유지 여부도 고려한다.
- max_tokens만 낮추면 JSON이 잘릴 수 있다. 출력 구조를 간결하게 만든 뒤 예산을 조정한다.
- 카탈로그 후보를 줄일 경우 검색 단계 재현율을 별도로 검증하고 범위 밖·정보 부족 처리를 유지한다.

공식 참고:
- [vLLM 구조화 출력](https://docs.vllm.ai/en/stable/features/structured_outputs/)
- [vLLM prefix caching](https://docs.vllm.ai/en/stable/features/automatic_prefix_caching/)

## 제안 5: 음성 핵심 정보 보존

실제 배포 STT 설정을 먼저 확인한다. 저장소에는 환각 억제 옵션 보강 기록이 있으므로 VAD 등을 미적용으로 단정하지 않는다.

무음 제거·발화 단위 처리, 기기명 힌트·정규화 사전, beam_size 변경을 비교하되 기기명·수치·부정 표현의 보존율을 함께 평가한다. 전체 전사 오류율만으로 위험 후보 추출의 품질을 판단하지 않는다. 과도한 무음 제거로 짧은 발화를 잘라내거나 용어 힌트가 없는 말을 만들어내는지도 확인한다.

공식 참고: [faster-whisper](https://github.com/SYSTRAN/faster-whisper)

## 검증 순서와 팀 논의 항목

1. AI 서버 담당: 업로드, 대기열, 모델 교체·로딩, 탐지·전사, LLM 입력 처리·출력 생성 시간을 분리 계측한다.
2. AI·계산 담당: 사진·텍스트·음성을 분리하고 첫 요청/연속 요청, 사진 수, 음성 길이, 동시 요청 조건을 기록한다.
3. 모델 상주와 키워드 선표시를 각각 비교한다. 변경을 한 번에 섞지 않는다.
4. 사람 검수된 정답으로 기기·키워드 정밀도/재현율, 사진당 오탐·미탐, 부정·수치 보존, 사용자 수정 횟수를 측정한다.
5. 지연은 중앙값(p50)·느린 요청(p95), 첫 표시·전체 완료를 나눠 보고한다. 정확도 허용 기준은 팀이 실험 전에 정한다.

실제 모델 호출 중단 상태는 저장소 지침에 따른다. 이번 문서 공유는 호출 재개나 서버 자원 변경을 승인한 것이 아니다. 최종 안전 판단과 미평가·정보 부족 처리, 현재 위험도 정책은 변경하지 않는다.

## 공유 범위

신규 문서 한 파일만 추가하는 검토용 변경이다. 실행 코드, 설정, 의존성, 기존 실험 결과, 모델, 배포는 변경하지 않는다. main 병합은 별도 검토 대상이다. 실제 데이터·자격증명·팀원 개인 이름은 포함하지 않는다.
