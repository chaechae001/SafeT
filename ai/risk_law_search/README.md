# 위험·법령 키워드 조회 (독립 확인용)

키워드를 넣으면 위험사례 카드(위험 후보)와 보유 법령 원문(법령 후보)을 함께 찾아 화면에 보여 준다.
설계 기준은 [위험성평가 카드 데이터 구조 제안](../../docs/chroma/risk-card-data-model-team-guide.md)이다.

- 상태: 확인용 독립 모듈. 서비스(평가표 저장·확정·위험도 계산)와 연결하지 않았다.
- 결과는 후보다. 위험 확정, 위험도 계산, 법령 적용 확정이 아니다. 최종 판단은 담당자가 한다.
- 검색: e5 임베딩 의미 점수 + 키워드 점수 혼합(기본). 저장은 LangChain Chroma. 외부 API 호출 없음(로컬 CPU 모델).

## 설치

혼합 방식은 전용 가상환경을 쓴다(백엔드 환경과 분리). 저장소 루트에서:

```
python -m venv ai/risk_law_search/.venv
ai/risk_law_search/.venv/Scripts/python -m pip install torch==2.15.0 --index-url https://download.pytorch.org/whl/cpu
ai/risk_law_search/.venv/Scripts/python -m pip install -r ai/risk_law_search/requirements.txt
```

Linux는 `Scripts/python` 대신 `bin/python`. 모델(`intfloat/multilingual-e5-small`, 약 470MB)은 처음 실행할 때 Hugging Face에서 내려받아 캐시에 둔다. 모델 가중치는 저장소에 올리지 않는다.

## 실행

```
# 1) 색인 만들기(처음 한 번, CPU 약 3분). 원본이나 모델이 바뀌면 다시 만든다.
ai/risk_law_search/.venv/Scripts/python -m ai.risk_law_search.server --build-index

# 2) 서버 실행(약 20초 후 준비). http://127.0.0.1:8020
ai/risk_law_search/.venv/Scripts/python -m ai.risk_law_search.server
ai/risk_law_search/.venv/Scripts/python -m ai.risk_law_search.server --host 0.0.0.0 --port 8020
```

모델 없이 키워드만 쓰려면 `--mode keyword`. 이때는 표준 라이브러리만 필요하다(어떤 Python 3.9+로도 실행).

| 옵션 | 환경변수 | 기본값 |
|---|---|---|
| `--mode` | `RISK_LAW_MODE` | `hybrid` (`keyword` 가능) |
| `--model` | `RISK_LAW_MODEL` | `intfloat/multilingual-e5-small` |
| `--index-dir` | `RISK_LAW_INDEX_DIR` | `ai/risk_law_search/.index` (Chroma 저장, git 제외) |
| `--data` | `RISK_LAW_DATA_DIR` | `docs/chroma` (법령 `*.hwpx`와 `risk_card_data.md`) |
| `--cards` | `RISK_LAW_CARD_FILE` | 데이터 폴더의 `risk_card_data.md` |
| `--as-of` | `RISK_LAW_AS_OF` | 오늘. 이 날짜 이후 시행 예정인 조문은 검색에서 뺀다 |
| `--host`, `--port` | `RISK_LAW_HOST`, `RISK_LAW_PORT` | `127.0.0.1`, `8020` |

인터넷이 없는 서버에서는 모델 캐시를 미리 복사하고 `HF_HUB_OFFLINE=1`로 실행한다.

카드–법령 연결 전체를 검토용 JSON으로 저장:

```
ai/risk_law_search/.venv/Scripts/python -m ai.risk_law_search.server --export-links card_law_links.json
```

## 배포

1. 서버에 위 설치를 한 번 한다.
2. `git pull` → `--build-index`(원본이 바뀐 경우만 실제로 임베딩) → 서버 재시작.
3. `GET /api/health`에서 `mode`, `model`, 컬렉션 이름, 원본 해시를 확인한다.

## 플랫폼 입력 분석 (화면 기본)

새 평가표 만들기(`POST /evals`)와 같은 입력을 받는다. 지금 플랫폼은 입력을 단위로 나누지 않고 한 문장으로 합쳐 처리한다. 이 모듈은 공유 규약의 검색 단위(`unit_id`)처럼 나눠서 처리한다.

```
POST /api/analyze
{"text": "주방에서 튀김기로 닭을 튀깁니다. 바닥에 기름이 묻어 미끄럽습니다.",
 "voice_text": "오토바이로 배달도 나가요.",
 "machines": [{"machine_code": "M01", "machine_nm": "튀김기"}, "덤웨이터"],
 "photos": []}
```

- 단위: 작업 설명·음성 전사문은 문장(마침표·물음표·느낌표·줄바꿈·세미콜론)마다, 등록 기기는 기기마다 하나. 같은 문장은 한 번만. 최대 60단위.
- 단위마다 위험요인 1~3개. 기준을 통과한 카드가 없으면 가장 가까운 1개를 `low_confidence`(기준 미달·확인 필요)로 붙인다.
  - 키워드 방식에서 낱말이 하나도 겹치지 않으면 0개일 수 있다.
- 위험요인마다 법령 1개: 카드와 가장 가까운 조문 1순위 → 없으면 카드에 적힌 법령 → 없으면 `law: null`과 사유.
- 위험요인마다 선택 항목 두 목록을 **각각 항상 3개** 준다. 처음에는 선택되지 않은 상태(`selected: false`)이며 화면에서 담당자가 고른다.
  - `current_options` **현재 조치 사항**: ① 이 카드 직접 대책 → ② 비슷한 카드들의 직접 대책. 현장에서 하고 있는 것만 선택한다.
  - `improvement_options` **개선 조치 사항**: ① 이 카드 보강 대책 → ② 비슷한 카드들의 보강 대책 → ③ 비슷한 카드들의 직접 대책. 적용할 것만 선택한다.
  - 한 단계에서 3개를 넘으면 입력 문장과 낱말이 많이 겹치는 순서로 고른다(입력 문장 낱말 2배, 카드 제목 낱말 1배, 드문 낱말일수록 큼).
  - 두 목록에 같은 문장은 넣지 않는다. 문장을 새로 만들지 않고 카드 자료의 대책만 쓴다.
  - 비슷한 카드: 혼합 방식은 카드 임베딩 코사인, 키워드 방식은 키워드 유사도로 상위 15개.
  - 항목마다 `origin`(이 카드 직접 대책 / 이 카드 보강 대책 / 유사 카드 직접 대책 / 유사 카드 보강 대책)과 `origin_card`(대책이 원래 적힌 카드)를 남긴다.
  - 항목 ID는 원래 대책 위치다: `<카드 ID>:M<번호>`(직접 대책), `<카드 ID>:X<번호>`(보강 대책).
  - 문구: 카드 원문 대신 간결한 방법 문구(`text`)를 보여 주고 원문은 `original`에 남긴다. 화면의 "카드 원문 보기"로 확인한다.
    - 정리표 `measure_actions.json`: 원문 314개 → 방법 문구(고유 283개). AI 보조 초안 · 검토 전. 실행 중 모델로 생성하지 않는다.
    - 규칙: '무엇을 어떻게 한다'(교육·설치·점검·지급·착용 지도 등)로 쓴다. '~금지·~않음·~행위'로 끝내지 않는다(예: "떨어지는 칼을 잡는 행위 금지" → "떨어지는 칼을 잡지 않도록 교육"). 32자 이하. 원문에 없는 조치는 더하지 않는다. 뜻이 같은 원문은 같은 문구로 맞추고, 목록에서는 문구 기준으로 중복을 뺀다.
    - 카드 자료가 바뀌어 정리표에 없는 원문이 생기면 원문 그대로 보여 주고 `action_reviewed: false`로 표시한다.
  - 카드 대책은 권장 조치이고 현장 사실이 아니다(지침서 1절). 고르지 않은 항목을 '미실시'로 해석하지 않는다. 다른 카드에서 채운 항목은 이 위험과 맞지 않을 수 있으므로 출처를 보고 고른다.
- 등록 기기 단위에는 "보유 기기이며 실제 사용·노출이 확인된 것은 아님"을 붙인다.
- 사진은 받기만 하고 분석하지 않는다(기기 탐지 미연결). 응답 `warnings`에 장수를 적는다.
- 부정 표현이 있는 문장은 결과를 숨기지 않고 `negation.found`와 경고로 표시한다.
- 입력 제한은 플랫폼과 같다: 작업 설명·음성 각 10,000자, 기기 100개, 사진 6장, 요청 본문 20MB.

## API

| 경로 | 내용 |
|---|---|
| `POST /api/analyze` | 플랫폼 입력 → 단위별 위험요인 1~3개, 위험요인별 법령 1개 |
| `GET /api/health` | 방식·모델·Chroma 컬렉션, 원본 파일 해시, 카드·법령 조각 수, 평가일 |
| `GET /api/search?q=키워드` | 위험 후보 카드와 법령 후보. `law_start=02`로 다음 문서부터 이어 찾기, `law_docs`로 멈추기 전 문서 수 |
| `GET /api/card?id=FOOD-01-H1` | 카드 한 건과 연결 법령 |
| `GET /api/links` | 카드–법령 연결 전체 |

각 결과의 `score`는 관련도(0~1), `score_detail`은 의미 점수(`semantic`)와 키워드 원점수(`keyword`)다.

## 처리 규칙

**법령 원문(HWPX)**
- 파일명 앞 번호(01, 02, …, 06, 06-02, 07, 08)로 문서 순서를 정한다. 번호가 없으면 오류.
- 조문 분리는 공유 규약 파서(`docs/rag-evidence-v1/parse_law_hwpx.py`)와 같다. 부칙은 제외, 삭제 조문은 검색 제외.
- 검색 단위는 항(①②…)이다. 호·목은 속한 항에 붙인다.
- 같은 번호 조문이 두 번 있고 뒤에 `[시행일: …] 제N조` 표시가 있으면 뒤의 것을 시행 예정 판으로 보존한다. 평가일 전이면 검색하지 않는다.
- 조각 ID: `law:<문서번호>@<시행일>:art<조>[-<가지>]:p<항>[:f<개정 시행일>]` 예: `law:02@20260302:art3:p1`.

**위험사례 카드**
- 원본 객체를 그대로 보존한다(`raw`). 카드 ID는 원본 ID를 쓴다.
- 직접 대책(`measures`)과 보강 대책(`measures_extra`, 다른 카드 출처)을 나눠 보여 준다.
- `laws`가 빈 배열이면 "미수록"으로 표시한다. "관련 법령 없음"이 아니다.
- 키워드 검색은 점검(check)·사례(case) 카드만 대상이다. 참고(reference) 카드는 대책 출처로만 남긴다.

**카드 검색 문장**
- 카드 고유 내용(기기명·사고 유형·제목·본문)만 임베딩하고 키워드 색인에 넣는다.
- 구역명·대상 작업·예시 작업은 같은 구역 카드가 똑같이 공유한다(예: 식재료 전처리 구역 카드는 위험이 제면기 말림이어도 '야채 절단'을 가짐). 이 공통 문구는 별도 키워드 색인에 두고 0.3 비중으로만 더한다.

**검색 점수(혼합)**
- 의미 점수: e5 임베딩 코사인. 문서는 `passage:`, 검색어는 `query:` 접두어. 검색어마다 중앙값 0 · 최고값 1로 맞춘다.
- 키워드 점수: TF-IDF 코사인. 최고값으로 나눠 0~1로 맞춘다.
  - 토큰화는 형태소 분석(kiwipiepy)으로 조사·어미를 뗀 명사·동사·형용사 어간이다. 예: '썰어요'·'썰기' → '썰', '넘어짐'·'넘어지거나' → '넘어지'. 2자 이상 명사는 글자 2개 조각도 더한다.
  - kiwipiepy가 없는 환경에서는 단어와 단어 안 글자 2개 조각으로 자동 전환한다(`/api/health`의 `tokenizer`).
- 법령 관련도 = 0.5·의미 + 0.5·키워드, 카드 관련도 = 0.6·의미 + 0.4·키워드. 벌칙·과태료·양벌규정 조문은 ×0.7.
- 카드 기준 통과 = 관련도 0.45 이상 + (키워드 원점수 0.1 이상 또는 모델 원점수 0.83 이상). 의미 점수를 검색어마다 0~1로 늘리기 때문에 절대 근거가 하나 더 필요하다. 의미 없는 입력("ㅁㄴㅇㄹ", "오늘 날씨가 좋네요")은 모델 원점수 0.81~0.82, 키워드 0이었다.
- 하다·되다·있다·없다 같은 흔한 동사는 키워드에서 뺀다("회의를 합니다"가 '하다'만으로 겹치던 문제).
- `synonyms.json`의 비슷한 말을 검색어에 덧붙인다(예: 오토바이 → 이륜차). 검토 전 초안이다.
- 부정 표현(없다·하지 않는다 등)이 있으면 경고를 띄운다. 결과를 숨기지 않는다.

**법령 순서 규칙**
- 01번 문서부터 차례로 보며 관련 조문이 나온 첫 문서에서 멈춘다. "다음 법령 문서에서 이어 찾기"로 다음 문서부터 계속 찾는다.
- 관련 조문 = 관련도 0.6 이상이면서 키워드 원점수 0.2 이상(형태소 토큰화 기준). 모델 점수만 높거나 한 글자 단어만 겹치는 조문은 인정하지 않는다(짧은 키워드에서 벌칙 조문, '칼'로 잠수작업 조문 등이 올라오는 것을 막음).

**카드–법령 연결**
- 카드 고유 내용(기기·사고 유형·제목·본문)으로 위 관련 조문 기준을 통과한 조각 상위 3개를 미리 연결한다. 이 연결은 순서 규칙 없이 전체에서 고른다.
- 대책 문장은 넣지 않는다. 넣었을 때 '용기·장갑' 같은 낱말이 엉뚱한 조문과 겹쳤고, 빼자 튀김기 폭발 → 제254조(화상 등의 방지), 물기 미끄러짐 → 제3조(전도의 방지)처럼 맞는 연결이 늘었다.
- 기준을 통과한 조각이 없으면 연결하지 않는다. 기준을 낮추면 엉뚱한 조문이 붙어서 낮추지 않았다.
- 알려진 어색한 1순위 연결(보유 법령에 맞는 조문이 없거나 약함): 식용유 화재(FOOD-04-C1) → 액화석유가스법 제56조(사고의 통보), 칼 베임(OPS-04-H2) → 안전보건규칙 제42조(추락의 방지), 칼 보관(FOOD-09-H2) → 제16조(위험물 등의 보관), 소화기 비치(EDU-H07) → 제628조(이산화탄소 소화기). 담당자 검토가 필요하다.
- 카드 `laws`에 적힌 법령은 법령명·조 번호로 보유 원문 조각에 따로 연결한다(`card_cited`). 시행령·시행규칙 등 보유하지 않은 법령은 "보유 법령 원문에 없음"으로 남긴다.
- 두 연결 모두 자동 연결이다. 적용 여부와 항·호 단위의 정확성은 담당자가 확인한다.

- `test_engine.py`(키워드 방식 12개): 문서 순서, 조각 ID·시행일, 시행 예정 조문 제외, 카드 대책 구분, 순서 멈춤, 이어 찾기, 카드–법령 연결, 부정 표현, 서버 응답.
- `test_hybrid.py`(혼합 방식 10개): 모델·저장소 표시, 다른 표현의 카드 찾기, 대표 키워드의 1순위 조문, 모델 단독 조문 차단, 순서 멈춤, 연결의 키워드 겹침, 형태소 활용형 일치, 구역 공통 문구가 카드 고유 위험을 앞서지 않음. 임베딩·형태소 패키지가 없으면 건너뛴다.

## 한계

- e5-small은 법령 문장에서 의미 구분이 약하다. 그래서 키워드 점수를 함께 쓰고, 키워드가 겹치지 않는 조문은 법령 후보에서 뺀다. 그 결과 "칼로 채소 썰기"처럼 보유 법령에 맞는 단어가 없으면 법령 후보가 0건이다(없다는 뜻이 아님).
- 형태소 분석은 같은 낱말의 활용형만 맞춘다. '썰다'와 '자르다·베이다'처럼 다른 낱말은 연결하지 못하고, 이때 e5-small 의미 점수만으로는 구분이 약하다. 그래서 칼 작업 동사(썰·썬다·썹니다·자르·잘라·다지)를 비슷한 말 사전에서 '칼·베임'에 연결했다. 다른 작업 표현도 같은 방식으로 사전에 추가한다.
- 순서 멈춤 규칙상 대부분 02(안전보건규칙)에서 멈춘다. 다른 법령은 이어 찾기로 확인한다.
- 법령 원문은 보유 HWPX 기준이다. 시행령·시행규칙·고시 별표는 없다.
- 가중치·기준점은 예시 키워드 13개로 정한 값이다. 정답셋으로 측정하지 않았다.
