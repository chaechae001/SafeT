## 1. 현재 라벨 형식 점검

| 항목 | 현재 상태 | 탐지에 필요한 것 |
|---|---|---|
| 단위 | 이미지 단위 기기 존재(멀티라벨) | 물체마다 박스 1개 |
| 영역 | 3x3 격자 칸(`region_grid`)과 칸을 합친 근사 박스(`bbox_norm_from_grid`) | 기기 윤곽에 맞는 박스 |
| 개수 | 한 이미지에 같은 기기는 1개 라벨(튀김기 3대도 1개) | 기기 인스턴스마다 1개 |
| 검수 | AI 보조 라벨, 사람 검수 전 | 사람 검수한 박스 |

결론: 지금 라벨은 **이미지 단위**다. 박스는 격자 근사라서 탐지 학습이나 mAP·IoU 평가에 쓸 수 없다. mAP는 박스 위치까지 맞춰야 점수를 주는 탐지 지표이고, IoU는 예측 박스와 정답 박스가 겹치는 비율이다.

그대로 쓸 수 있는 평가는 **이미지 단위 존재 여부** 평가다. 탐지 결과를 이미지별 equipment_id 집합으로 줄여 정밀도·재현율을 낸다. S03 화면도 이미지별 '있음/없음'만 쓰므로 1차 평가로 충분하다.

### 1.1 로컬에서 만든 박스 초안

`preannotations/`에 격자 근사 박스를 COCO 형식과 YOLO 형식으로 바꿔 두었다.

- 탐지 대상(`detection_target=yes`) 34개 클래스만 넣었다. 보류 클래스 라벨 5개(폐유통 2, 전기설비 3)는 뺐다.
- 주석 72개. 모든 주석에 `box_quality=grid_approx`를 달았다.
- 용도: 라벨 도구(CVAT, Label Studio 등)에 사전 주석으로 불러와 사람이 박스를 고치는 출발점. **학습·mAP 평가에 그대로 쓰지 않는다.**
- 같은 기기가 여러 대면 사람이 박스를 나눠야 한다(예: 튀김기 3대).
- 원본 사진은 옮기거나 바꾸지 않았다. 파일 경로만 참조한다.

### 3.1 Elice 인스턴스 사양 반영 (2026-11-16 추가)

사용자가 알려 준 사양이다. 인스턴스에서 직접 확인하지는 않았다(`nvidia-smi` 미실행).

| 항목 | 값 |
|---|---|
| 인스턴스 유형 | G-NAHPM-10 |
| GPU | NVIDIA A100 80GB PCIe를 MIG로 나눈 1g-10GB 조각 |
| CPU | 2 vCore |
| 메모리 | 24GiB |
| 스토리지 | 512GiB |

MIG(Multi-Instance GPU)는 GPU 한 장을 여러 조각으로 나눈 것이다. 1g-10GB는 A100 연산 자원의 약 1/7과 GPU 메모리 10GB를 쓴다. 따라서 A100 한 장 전체 성능을 기대하면 안 된다.

| 방안 | 이 사양에서의 판단(추정, 미측정) |
|---|---|
| (a) 소형·중형 YOLO 추론 | 가능할 것으로 본다. 34장 평가는 부담이 작다 |
| (b) 오픈 어휘 탐지 추론 | 소형 백본(예: Grounding DINO Swin-T, YOLO-World 소형)은 10GB 안에 들어갈 가능성이 높다. 대형 백본과 고해상도 입력은 메모리 부족 위험이 있다. 이미지 1장씩(배치 1) 처리로 시작한다 |
| (c) 파인튜닝 | 소형 YOLO를 작은 배치로 학습하는 것은 가능할 것으로 본다. 대형 모델·큰 입력·큰 배치는 10GB에서 어렵다 |
| 공통 병목 | CPU 2코어라서 이미지 디코딩·증강(데이터 로더)이 GPU보다 먼저 느려질 수 있다. 원본 5712x4284 사진 9장은 미리 축소해 두는 편이 낫다. 축소본은 원본과 별도 폴더에 둔다 |

### 3.2 SAM 3 후보 검토 (2026-11-16 추가)

사용자가 YOLO 대신 SAM 3를 제안했다. 웹 검색으로 확인한 내용이다(2026-11-16). 직접 실행하지 않았다.

| 항목 | 확인 내용 | 출처 |
|---|---|---|
| 방식 | 짧은 텍스트 프롬프트(명사구)로 해당 개념의 모든 인스턴스를 찾음. 마스크·박스·점수를 냄 | facebookresearch/sam3 README |
| 크기 | 약 848M 파라미터. 디스크 약 3.4GB | README, Roboflow |
| 환경 | Python 3.12+, PyTorch 2.7+, CUDA 12.6+ | README |
| 라이선스 | SAM License(자체 라이선스). 가중치는 Hugging Face에서 약관 동의 후 받음. 상업 이용 조건은 미확인 | README, HF 모델 카드 |
| 메모리 | 공식 이미지 기준 수치 없음. 비공식 fp16 측정 1024px 이미지 약 2GB 사례만 있음 | 커뮤니티 측정 |

판단(제안):

- SAM 3는 방안 (b) 오픈 어휘 탐지 자리에 들어갈 수 있다. COCO에 없는 튀김기·배기후드도 프롬프트로 시험할 수 있다.
- 기기마다 박스와 마스크를 함께 준다. 마스크는 VLM 상태 관찰(기기 주변 물기·적재)의 영역 근거로도 쓸 수 있다.
- 출력 형식 v2는 그대로 쓸 수 있다. `detector.model_name=sam3`, `class_map_match=open_vocab`, `prompt_set_version`을 채운다. 마스크는 v2에 없으므로 필요하면 선택 필드로 추가한다.
- 위험: 1g-10GB MIG에서 이미지 1장 추론이 들어갈 가능성은 있으나 미측정. 연산 자원이 1/7이라 장당 시간이 길 수 있다. 업소용 기기 영문명(예: commercial deep fryer)과 염지기 같은 국내 기기를 잘 찾는지는 미확인. SAM License가 서비스 배포에 맞는지 확인 필요.
- 권장: 34장 이미지 단위 비교에서 SAM 3를 (b)의 첫 후보로 넣고, 소형 YOLO 사전학습(a)과 같은 규칙으로 비교한다.

실행 전에 할 일:

- `nvidia-smi`로 MIG 조각과 메모리를 확인한다.
- 첫 실행 때 최대 GPU 메모리와 장당 처리 시간을 기록한다. 이 값은 Cloud 작업 기록 항목이다.

## 4. 권장 순서 (제안)

1. **평가셋 사람 검수**: 34장 이미지 단위 라벨을 사람이 확인한다. 이것이 모든 방안의 공통 기준이다.
2. **(a)와 (b) 무학습 비교**: 같은 34장에서 이미지 단위 정밀도·재현율을 기기별로 낸다. (a)는 직접 대응 5개 기기, (b)는 탐지 대상 34개 기기.
3. **판단**: 튀김기·가스레인지·배기후드·냉장고처럼 라벨이 많은 기기에서 (b)가 쓸 만한지 본다.
4. **(c) 준비**: 부족한 기기만 골라 학습 데이터를 모은다. 학습 권한이 있는 사진이어야 한다. 박스 라벨은 `preannotations/`를 출발점으로 쓸 수 있다.
5. **라이선스 결정**: 서비스 배포 방식에 맞춰 AGPL-3.0 사용 여부를 팀이 정한다. Ultralytics 외 대안도 같이 비교한다.

## 6. VLM 상태 관찰과의 경계

- 기기 탐지(무엇이 있나)는 탐지 모델이 맡는다. 출력은 equipment_id와 박스다.
- 상태 관찰(물기, 적재, 기름때 등)은 VLM이 맡는다. 이 문서는 VLM 출력 형식을 정하지 않는다.
- VLM이 특정 기기 주변 상태를 보려면 탐지 박스를 근거로 받을 수 있다. `detection_refs`를 함께 넘기는 방식을 제안한다. 연결 방식은 상태 관찰 트랙과 맞춰야 한다.
- 이 변경으로 `261115_AI출력계약_신호기준_DR`의 S04 입력 중 사진 처리 부분이 바뀔 수 있다. 그 문서는 이 세션이 고치지 않았다.
