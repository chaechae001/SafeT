### 2.2 (a) 기기 인식 결과

- 탐지 모델 원 응답은 기존 형식 v2를 그대로 쓴다. 등록 기기 제외 규칙 R1–R8도 그대로다(`261116_기기인식_출력형식_제외규칙_v2_DR.md` 3절).
- 새로 더한 것은 사용자 확인본 `equipment_confirmed.v2`다.
  - `origin`: `detected` / `registered` / `user_added`
  - `user_action`: `kept` / `relabeled` / `added` / `removed`
  - `relabeled`이면 `original_equipment_id`(탐지 모델이 낸 원래 ID)가 필수다. 탐지 오류 분석에 쓴다.
  - `removed` 항목도 남긴다. LLM 요청에서는 뺀다.
- 탐지가 실패해도(`detection_status=failed`) 사용자가 직접 추가해 다음 단계로 갈 수 있다.

### 2.3 (b) 기기별 위험요인 후보

후보 1개의 필드:

| 필드 | 필수 | 내용 |
|---|---|---|
| `candidate_id` | 예 | 후보 ID |
| `work` | 아니요 | 관련 작업 |
| `hazard` | 예 | 위험요인 문구(위험한 상황과 결과) |
| `accident_type` | 예 | `{code, label}`. 코드 후보는 기기 마스터 `hazard_codes` 14개(burn, cut, slip 등) |
| `rationale` | 예 | 추천 근거 문장. 출처 내용 요약만. 위험 정도 판단 문구(높다·낮다)는 쓰지 않음 |
| `source_refs[]` | 예, 1개 이상 | 출처 ID. RAG 지식베이스의 `row_id`(예: `CHK-4-2-3-01`, `CASE-FOOD_A_01`)나 `chunk_id` |
| `measure_candidates[]` | 예(빈 배열 가능) | 예방대책 후보. 각 대책에도 `source_refs` 1개 이상, `control_type`(고시 제12조 순서) |
| `laws[]` | 아니요 | 검증된 조항만(v1과 같음) |

강제 규칙(스키마로 검사):

- 후보에 `signal`, `risk_score`, `risk_level`, `likelihood`, `severity`, `expected_signal`, `post_signal`이 있으면 거부한다.
- 출처 없는 후보·대책은 거부한다. 근거를 못 찾은 기기는 `group_status=no_source_found`, 후보 0개로 둔다. 사용자는 직접 추가로 진행한다.
- 기기 하나만 실패하면 그 그룹만 `failed`이고 응답은 `partial`이다.
- 후보와 대책은 모두 미선택으로 화면에 나간다.

### 2.4 (c) 사용자 선택 결과

| 필드 | 내용 |
|---|---|
| `scale_id`, `scale_version` | 어떤 척도로 골랐는지. 척도가 바뀌어도 당시 값을 해석할 수 있게 한다 |
| `selections[].origin` | `ai_candidate`(후보 선택) / `user_custom`(직접 입력) |
| `hazard`, `hazard_edited` | 후보 문구를 고쳤는지 남긴다 |
| `likelihood`, `severity` | `{level, label}`. 사용자가 직접 고른 값 |
| `current_measures[]` | 현재 시행 중인 조치. 가능성·중대성은 현재 조치를 고려해 고른다(23년 안내서 61쪽) |
| `selected_measures[]` | AI 후보 대책 + 직접 추가 대책 |
| `phase` | `before_measures`(평가 시점) / `after_measures`(대책 실행 후 다시 고른 값) |
| `decided_by` | 항상 `user` |

등급이 척도 범위 안인지는 스키마가 아니라 서버가 `scale_id` 설정으로 검사한다.

### 2.5 (d) 규칙 기반 위험도 계산

- 규칙 설정(`risk_rule_config.v2`)에 척도 등급, 조합 방법(`product` / `sum` / `matrix_lookup`), 점수 구간을 담는다. 등급과 구간마다 근거 문서·쪽을 붙인다.
- `adoption_status`가 `adopted`인 설정만 운영에 쓴다. 지금 있는 설정은 안내서 예시뿐이다(`guide_example_not_adopted`).
- 계산 결과(`risk_result.v2`)는 `computed_by=rule_engine`으로 고정한다. 같은 입력과 같은 규칙 버전이면 항상 같은 결과다.
- `result_status`: `computed` / `not_rated`(사용자가 아직 고르지 않음) / `out_of_scale`(척도 밖 값).
- `signal`은 설정의 구간에 색 대응이 있을 때만 채운다. 대응이 없으면 null이다.
- 채택 규칙이 없으면 전체 `status=rule_not_adopted`로 둔다. 시험 계산은 할 수 있지만 운영 화면에 내지 않는다.

## 3. 발생 가능성·중대성 척도와 계산식의 선택지

이 문서는 척도를 정하지 않는다. **어떤 척도를 쓸지는 팀·전문가 결정 필요**다. 아래는 `RAG용/` 안내서에서 찾은 선택지다. 쪽 표기는 "인쇄 쪽(PDF 쪽)"이다.

### 3.1 공통 원칙 (모든 선택지에 적용)

| 원칙 | 근거 |
|---|---|
| 빈도·강도의 산출 기준은 사전준비 단계에서 근로자와 상의해 미리 정한다 | 쉽고 간편한 33쪽(PDF 37), 23년 61쪽(PDF 76) |
| 곱셈만이 아니라 덧셈·행렬 조합도 쓸 수 있다 | 쉽고 간편한 33쪽(PDF 37), 23년 60쪽(PDF 75) |
| 현재 위험성을 정할 때 현재 시행 중인 안전보건조치를 고려한다 | 쉽고 간편한 33쪽(PDF 37), 23년 61쪽(PDF 76) |
| 위험성 결정은 사전에 확정한 기준으로 한다(고시 제11조 개정 요지) | 23년 PDF 13 |
| 감소대책 실행 후 위험성을 다시 결정한다(고시 제12조 제2·3항) | 23년 96쪽(PDF 111), 98쪽(PDF 113) |
| 부상 정도만 기준으로 쓰면 대책 후 등급이 잘 바뀌지 않는다. 안전관리 상태 기준을 추가해 보완해야 한다 | 23년 156쪽(PDF 171) |

마지막 원칙은 v2 설계에 중요하다. 중대성(부상 정도)은 대책 후에도 그대로인 경우가 많다. 그래서 사용자가 대책 후 가능성만 낮추게 될 수 있다. 등급 문구에 안전관리 상태를 넣을지 함께 정해야 한다.

### 3.2 선택지 비교

| 번호 | 방법 | 척도·계산 | 구간·허용 기준 | 근거 (문서·쪽) | 흐름 ④와 맞는지 | 한계 |
|---|---|---|---|---|---|---|
| S1 | 빈도·강도법 3×3 (KRAS 예시) | 빈도 1–3(거의 없음: 3개월에 1회 정도 / 가끔: 1주일에 1회 정도 / 빈번: 1일에 1회 정도) × 강도 1–3(소: 비치료 / 중: 휴업 필요 / 대: 사망·장애). 곱셈 → 1, 2, 3, 4, 6, 9 | 예시: 1–3 허용 가능(필요시 개선), 4–9 허용 불가능(개선책 마련·이행) | 쉽고 간편한 33–34쪽(PDF 37–38), 23년 61–62쪽(PDF 76–77) | 맞음 | 2개 구간뿐. 빨강·노랑·초록 3구간 경계 근거 없음. 모두 "예시" |
| S2 | 빈도·강도법 5×4 (KRAS 제공) | 이름만 나옴 | 근거 없음 | 23년 61쪽(PDF 76), 쉽고 간편한 30·33쪽(PDF 34·37), 민간재해예방기관 매뉴얼 PDF 63 | 맞음 | 각 등급 정의가 `RAG용/`에 없음. KRAS 원문 확인 필요 |
| S3 | 4×4 행렬 (CHARM) | 노출수준(가능성) 1–4 × 유해성(중대성) 1–4 = 1–16 | 1–2 낮음, 3–4 보통(필요에 따라 개선), 5–11 높음(연간계획에 따라 개선), 12–16 매우 높음 | 쉽고 간편한 45쪽(PDF 49), 51쪽(PDF 55) | 형식은 맞음 | **화학물질 위험성평가용.** 음식점 물리적 위험(화상·베임 등)에 쓰는 근거 없음. 구간 표의 허용 여부 배치는 원문 그림 확인 필요 |
| S4 | 위험성 수준 3단계 판단법 | 상·중·하(빨강·노랑·초록)를 사용자가 직접 고름. 가능성·중대성을 나누지 않음 | 예시: 하만 허용 | 쉽고 간편한 12–13쪽(PDF 16–17), 23년 51쪽(PDF 66), 23년 156쪽(PDF 171) | **다름**(④는 가능성·중대성을 따로 고름) | 계산식이 없어 "규칙 기반 계산"이 등급 표시뿐임. 3색과 직접 대응하는 근거는 가장 분명함 |
| S5 | 5단계 판단법 | 매우 높음–매우 낮음을 직접 고름. 예시 기준: 사망·영구장해 / 6개월 이상 휴업 / 3–6개월 휴업 / 3개월 미만 휴업 / 휴업 불필요 + 안전관리 상태 문구 | 예시: 위 2단계 허용 불가능 | 23년 156쪽(PDF 171), 민간재해예방기관 매뉴얼 39쪽(PDF 45) | 다름 | S4와 같음. 3색 대응 근거 없음 |
| S6 | 체크리스트법 | 적정 / 보완 | 적정=허용 가능, 보완=허용 불가능 | 23년 47쪽(PDF 62), 쉽고 간편한 19쪽(PDF 23), 소규모 사업장 안내서 11·13쪽(PDF 15·17) | 다름 | 2단계뿐 |

참고(`RAG용/` 밖, 근거 아님):

- `261113_restaurant_completed_assessments_DR`의 공개 음식점 평가 사례 8건은 가능성 최대 3, 중대성 최대 4를 쓴다(예: 2×4=8). 실제 현장에서 3×3보다 큰 척도를 쓴다는 단서다. 척도 정의는 확인하지 않았다.
- 사례 FOOD_A_05는 원문에 "2×4인데 위험성 12"로 적혀 있다(RAG 세션 인계 메모). 규칙 계산이 필요한 이유의 예로 쓸 수 있다.
- 사용자 시안의 3×3 "6/9"는 시안에 예시라고 적혀 있다. 안내서에서 같은 구간 근거를 찾지 못했다. 그래서 예시 설정 파일에 넣지 않았다.

### 3.3 신호등(3색)을 유지할 경우

| 안 | 내용 | 근거 상태 |
|---|---|---|
| T1 | 3×3 점수 구간을 3개로 나눠 빨강·노랑·초록에 대응 | 경계 근거 없음. **팀·전문가 결정 필요** |
| T2 | 안내서 예시처럼 허용 가능·불가능 2단계만 표시(신호등 폐지 또는 2색) | 근거 있음(S1). 결정 1 변경 필요 |
| T3 | S4(3단계 판단법)로 바꿔 사용자가 상·중·하를 직접 고름 | 3색 근거 가장 분명. 흐름 ④의 가능성·중대성 분리와 다름 |
| T4 | 가능성·중대성 등급은 기록만 하고, 허용 여부와 개선 시급성(즉시 / 가능한 빨리 / 현재 상태 유지)은 사용자가 따로 고름 | 쉽고 간편한 26쪽(PDF 30)의 개선 방법 표와 맞음. 입력이 늘어남 |

규칙 설정 파일은 T1–T4 모두 담을 수 있다(`bands[].signal`, `method`). 예시 파일 `examples_v2/risk_rule_config.guide_3x3_example.json`은 S1을 그대로 옮기고 `signal`을 모두 null로 두었다.

## 4. 화면설계서 v3.19와 충돌하는 부분

화면설계서는 팀 문서이므로 수정하지 않았다. 아래 "대체 방안"은 이 문서의 제안이고, 모든 항목은 팀 결정이 필요하다.

| 번호 | v3.19 내용 | 쪽 | v2 방향과 충돌 | 대체 방안 | 팀 결정 필요 |

## 5. 검증

### 5.1 결과 (2026-11-16, 로컬)

- 방법: Python `jsonschema`(Draft 2020-12), 임시 환경(`uv run --with jsonschema`). 프로젝트에 의존성을 추가하지 않았다.
- 메타 스키마: v2 스키마 7개와 참조한 탐지 응답 v2 스키마 1개 통과.
- 예시: v2 예시 5개 유효. 탐지 응답 v2 예시(`model_output` 부분)도 유효.
- 경계 사례 21개 모두 기대대로 통과·거부. 거부를 확인한 경우:
  - LLM 후보에 `signal`·`risk_score`·`likelihood`·`severity`·`risk_level`·`expected_signal`이 있음
  - 출처 없는 후보·대책, 출처 없음 그룹에 후보 동봉, 정상 그룹에 후보 0개, 검증 안 된 법령
  - 사용자 선택의 `decided_by=ai`, 가능성 누락, AI 후보인데 `candidate_id` 없음, 조치 후 값에 원 항목 ID 없음
  - 계산 결과의 `computed_by=llm`, 미입력인데 점수 있음
  - 라벨 수정인데 원래 ID 없음
- 규칙 재계산: 예시 선택값 2건을 예시 설정(S1)으로 다시 계산해 예시 결과와 일치(6→허용 불가능, 2→허용 가능). 설정의 구간이 가능한 점수 {1, 2, 3, 4, 6, 9}를 한 번씩만 덮는 것도 확인.
- ID 대조: 예시의 기기 ID(고유 5개)가 모두 기기 마스터에 있고, 출처 ID 2개(`CHK-4-2-3-01`, `CHK-4-2-3-02`)가 RAG 구조화표에 있음.
- 합계 32개 검사 통과. v1 검사(25개)도 다시 돌려 그대로 통과했다(v1 파일 변경 없음).

### 5.2 검증하지 않은 것

- 실제 LLM이 이 형식을 지키는지(출처 ID 환각 포함)는 실행하지 않았다.
- 규칙 엔진 코드는 만들지 않았다. 위 재계산은 검증 스크립트 안의 참조 계산이다.
- `uri` 형식, 척도 등급 범위 검사(서버 몫)는 확인하지 않았다.

| 위험도 계산 | 백엔드 정책 `CATALOG-MVP-1.0`을 따른다 | 사용자 지시(2026-11-17), SafeT main `1daa5d8`(#10) |

이 결정으로 3절의 가능성×중대성 척도 선택지와 8절의 3×3 결정은 계산 기준으로 쓰지 않는다. 기록으로만 남긴다.

### 9.2 백엔드 정책 요약 (`backend/domain/risk_policy.py`)

- 피해 수준 S1~S3은 카탈로그 시나리오가 정한다(`contracts/catalog_risk/catalog.json`). 사용자는 고르지 않는다.
- 조치 구간: C1=필요한 조치 모두 선택, C2=핵심 조치는 모두 선택, C3=핵심 조치 미선택.
- 등급: S×C 표로 상·중·하. 신호는 상=R, 중=Y, 하=G, 미응답=N(판단 필요).
- 예상 위험도는 현재 조치에 계획 조치를 더해 같은 함수로 계산한다. 현재 결과는 바뀌지 않는다.
- 이 표는 팀 MVP 운영 규칙이다. 전문가가 승인한 안전 기준이 아니다.

### 9.3 스키마 변경 (`schemas_v2_1/`, `examples_v2_1/`)

| 파일 | 변경 |
|---|---|
| common.v2_1 | 시나리오 ID, 조치 ID, 정책 버전, 등급, 신호 정의 추가 |

| risk_result.v2_1 | 백엔드 결과 형식으로 교체. `computed_by=backend_risk_policy`, `phase=current/expected`, `status=calculated/needs_information/not_in_catalog` |

### 9.4 검증 (2026-11-17, 로컬)

- v2.1 스키마 7개가 JSON Schema 2020-12 메타스키마 검사를 통과했다.
- 예시 2개가 스키마 검사를 통과했다. 오류 주입 3건(계산 안 된 항목의 등급, '조치 없음'과 조치 ID 동시 입력, 사용자 중대성 입력)은 모두 거부되었다.
- 카탈로그 26개 시나리오의 시나리오·조치 ID가 모두 정의한 형식과 맞았다.
- 예시 값(ENV, 현재 상·C3 / 예상 중·C2)이 백엔드 `evaluate` 함수 결과와 같았다.

### 9.5 남은 일

- 파이프라인(`hitl_graph.py`, `risk_rule.py`)은 아직 v2와 3×3 임시 규칙을 쓴다. v2.1과 백엔드 정책 호출로 바꿔야 한다.
- 후보 → 카탈로그 시나리오 연결 방법(키워드·LLM 선택)과 정확도는 아직 시험하지 않았다.
- 카탈로그에 없는 기기·위험(예: 염지기)은 `not_in_catalog`로 판단 필요가 된다. 카탈로그 확장은 팀이 정한다.
