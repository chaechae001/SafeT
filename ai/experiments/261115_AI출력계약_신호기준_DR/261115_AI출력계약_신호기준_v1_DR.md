# Safe-T AI 출력 계약과 신호 판단 근거 (v1 초안)

| 항목 | 내용 |
|---|---|
| 작성일 | 2026-11-15 (Asia/Seoul) |
| 작성 | DR (Claude 보조 작성, 팀 검토 전) |
| 기준 문서 | `261115_SafeT_화면설계서_v3.19_통합본_SH_v3.pdf` (41쪽, 결정사항 15개) |
| 근거 문서 | `RAG용/` 안내서 4종 (8장 출처 목록) |
| 상태 | 초안. 팀·개발자 확인 전이며 확정 요구사항이 아님 |
| 산출물 | 이 문서, `schemas/` JSON 스키마 10개 + 공통 정의 1개, `schemas/progress_stages.json`, `examples/` 응답 예시 3개 |

> 이 문서는 AI가 만드는 값의 **형식**을 정한다. 신호를 가르는 **위험성 판단기준 자체는 정하지 않는다.** 판단기준은 사업장(팀·전문가)이 미리 정해야 한다는 것이 안내서의 원칙이다(4.1절).

---

## 1. 요약

- AI 호출은 4개 시점, 5개 API로 나눈다: S04 초안 생성, S07 후보 보기, S07 선택 항목 추가, S05-D 예상 신호 판단, F03 조치 후 신호 재산정.
- 모든 신호 값은 `red | yellow | green | off` 네 가지다(34쪽). AI가 판단하지 못하면 항상 `off`(판단 필요)로 둔다.
- AI 응답에는 사용자가 확인해 저장하는 값(현재 조치 선택, 대책 체크, 담당자·예정일, 실제 결과)을 넣지 않는다. 스키마가 이를 거부한다.
- 안내서는 "상·중·하를 **빨강·노랑·초록 등** 3단계로 구분"하는 방법을 직접 제시한다(23년 안내서 51쪽, 쉽고 간편한 안내서 12쪽). 따라서 신호 3색은 **위험성 수준 3단계 판단법**에 대응시키는 것이 근거가 가장 분명하다.
- 각 등급의 판단기준(사망·장애, 요양, 경미 등)은 안내서에 **예시**로만 있다. 이를 Safe-T 기준으로 채택할지는 팀·전문가 결정이 필요하다.

## 3. 호출 시점별 계약

### 3.1 공통 규칙

| 규칙 | 내용 | 근거 |
|---|---|---|
| 응답 형식 | `{request_id, call, status}` + 성공 시 결과, 실패 시 `error` | 스키마 |
| status | `ok` 전부 정상 / `partial` 일부 항목 off 또는 추천만 실패 / `failed` 호출 전체 실패 | 15, 25쪽 |
| 요청 ID | 클라이언트가 `request_id`를 만든다. 현재 화면의 요청 ID와 다른 응답은 버린다 | 15쪽 늦은 응답 |
| 중복 방지 | 같은 `request_id` 재전송은 한 번만 처리한다 | 38쪽 중복 클릭 |
| 진행률 | 서버는 단계가 끝날 때 `ProgressEvent`를 보낸다. 단계 안 보간은 클라이언트가 다음 단계 값 미만으로 한다 | 15쪽 |
| 100% | 서버 저장 성공 응답 후에만 보낸다 | 25, 39쪽 |
| 법령 | `verified: true`인 조항만 넣는다. 검증 실패 조항은 빼고, 빈 배열도 허용한다 | 20, 28쪽 |
| 시각 | ISO 8601, `+09:00` | 프로젝트 규칙 |
| 개인정보 | 작성자·참여자·담당자 이름은 AI 요청에 넣지 않는다 | 데이터 최소화(제안) |
| 판단기준 | 요청·응답에 `criteria_version`을 싣는다. 팀 확정 전에는 null | 4장 |

### 3.2 S04 초안 생성

- 스키마: `s04_draft.request.schema.json`, `s04_draft.response.schema.json`
- 호출: 입력 01~03 완료 후 "초안 생성". 실패하면 입력을 유지하고 재시도한다.
- 입력: 업종, 기기 스냅샷(등록 기기 + 선택한 AI 인식 기기), 사진·글·음성 전사문(하나 이상).
- 출력: `items[]` = `RiskItemAI`. 항목마다 작업·위험요인·사고 유형·원인·설명·신호·판단 이유·모델 버전·법령·현재 조치 후보·추천 대책.

| 진행률 | 단계 코드 | 처리 | 쪽 |
|---|---|---|---|
| 20% | `analyze_input` | 입력 분석(사진·글·음성·기기 정리) | 15 |
| 40% | `generate_items` | 위험 항목 생성, RAG 검색 | 15 |
| 60% | `judge_signal` | 신호·판단 이유, 법령 검증, 현재 조치 후보 | 15 |
| 80% | `recommend_measures` | 빨강·노랑 추천 대책 3개, 스키마 검증 | 15 |
| 100% | `save_draft` | 백엔드 저장 성공 → S05 | 15 |

추천 대책 규칙(스키마 `oneOf`로 강제):

| signal | recommendation_status | recommended_measures |
|---|---|---|
| red, yellow | `ok` | 정확히 3개 |
| red, yellow | `failed` | 0개. 재시도·직접 추가로 보완(15쪽). 빈 대책으로 완료 처리하지 않음(21쪽) |
| green | `ok` 또는 `not_applicable` | 3개 또는 0개. 6장 확인 필요 |
| off | `not_applicable` | 0개 |

### 3.3 S07 키워드로 위험 추가

두 번 호출한다. 후보에는 신호를 만들지 않는다.

| 호출 | 스키마 | 입력 | 출력 | 진행률 |
|---|---|---|---|---|
| 후보 보기 | `s07_candidates.*` | 키워드(필수), 업종, 기기, 기존 작업·위험 조합 | `candidates[]` (작업·위험요인·사고 유형) | 설계서에 없음. 원형 로딩 제안 |
| 선택한 항목 추가 | `s07_add.*` | 체크한 후보 1개 이상 | `items[]` = S04와 같은 `RiskItemAI` | 25 → 50 → 80 → 100 |

선택한 항목 추가의 진행률(25쪽):

| 진행률 | 단계 코드 | 처리 |
|---|---|---|
| 25% | `analyze_candidates` | 위험 후보 분석, 중복 조합 재확인 |
| 50% | `judge_signal` | 신호 판단 |
| 80% | `measures_and_candidates` | 대책·현재 조치 후보 |
| 100% | `saved` | 저장 성공 → S05 |

### 3.4 S05-D 저장·확정 때 예상 신호

- 스키마: `s05d_expected_signal.*`
- 호출 대상: 지난 판단 이후 대책이 바뀌었거나 아직 판단하지 않은 항목. 대책이 1개 이상인 빨강·노랑, `green_choice=add`인 초록.
- 바뀐 대책 판정: 응답의 `measures_considered`를 저장하고 다음 저장 때 비교한다(제안).
- 바뀐 항목이 없으면 AI를 호출하지 않는다. 원형 로딩만 짧게 보여준다(25쪽).

| 동작 | 진행률 단계 (25쪽) |
|---|---|
| 평가표 저장 | 저장 30% `save_data` → 예상 신호 판단 70% `judge_expected_signal` → 완료 100% |
| 평가표 확정 | 남은 예상 신호 판단 50% → 후속업무 집계 80% → 확정 처리 100% → S08 |

실패하면 입력은 저장하고 해당 항목의 `expected_signal`만 `off`로 둔다. off가 남으면 확정할 수 없다(25쪽).

### 3.5 F03 결과 저장 후 조치 후 신호

- 스키마: `f03_post_signal.*`
- 순서: 백엔드가 실제 결과를 먼저 저장(`status=done`)한 뒤 AI를 호출한다. 결과 저장과 조치 완료는 AI 성공 여부와 무관하다(결정 9, 40쪽).
- 입력: 항목 정보, 계획 대책, 예상 신호, 실제 결과·완료일·조치 후 사진, 회차.
- 출력: `post_signal`, `post_signal_reason`, `evidence_used`(결과 문장 사용 여부·사진 ID), `judged_at`, `model_version`, `followup_needed`.

| 진행률 | 단계 코드 | 처리 (39쪽) |
|---|---|---|
| 15% | `validate` | 필수값 확인. 누락이면 여기서 멈추고 해당 칸으로 이동 |
| 35% | `save_result` | 결과·사진 저장 |
| 65% | `recompute_post_signal` | 조치 후 신호 AI 재산정 |
| 85% | `update_followups` | 후속업무 갱신 |
| 100% | `done` | F03-R 산정 결과 |

### 3.6 실패 처리 요약

| 상황 | 저장 값 | `off_reason_code` | 화면 | 확정 영향 |
|---|---|---|---|---|
| S04 전체 실패 | 저장 안 함 | (`error.code`) | 입력 유지, 재시도 | 해당 없음 |
| 항목 신호 판단 실패 | `signal=off` | `ai_error` 등 | 판단 필요(모두 꺼짐) | 확정 불가 |
| 항목 추천 대책만 실패 | 신호 유지, `recommendation_status=failed` | null | 재시도·직접 추가 | 대책 1개 이상 필요 |
| 응답이 스키마 위반 | 해당 항목 `off` | `invalid_output` | 판단 필요 | 확정 불가 |
| 입력이 부족해 판단 불가 | `off` | `insufficient_input` | 판단 필요 | 확정 불가 |
| 판단기준 미설정 | `off` | `criteria_not_set` | 판단 필요 | 확정 불가 |
| 예상 신호 판단 실패 | `expected_signal=off` | 원인 코드 | 다시 판단 제공 | 확정 불가(25쪽) |
| 조치 후 신호 실패 | `post_signal=off`, 조치 완료 유지 | 원인 코드 | 다시 산정만 제공 | 5.2절 |
| 사용자가 입력으로 돌아감 | 응답 무시 | (`cancelled`) | 입력 화면 유지 | 해당 없음 |

`off`를 다시 판단하는 API는 설계서에 버튼만 있고 호출 형식이 없다. 같은 스키마를 항목 1건으로 다시 부르는 방식을 제안한다(6장).

## 4. 신호 판단 기준의 근거

### 4.1 원칙: 판단기준은 사업장이 미리 정한다

| 내용 | 근거 |
|---|---|
| 사전준비 단계에서 위험성의 수준과 판단기준을 정한다 | 23년 안내서 7쪽(PDF 22) |
| 위험성 결정은 사전에 확정한 기준으로 한다(고시 제11조 개정 요지) | 23년 안내서 PDF 13쪽(개정 요약표) |
| 각 단계의 수준과 판단 방법은 준비 단계에서 미리 정한 기준을 쓰고, 현재 안전·보건 조치도 고려한다 | 23년 안내서 51쪽(PDF 66), 쉽고 간편한 안내서 12쪽(PDF 16) |
| 판단기준과 허용 가능 수준을 정할 때 근로자가 참여해야 한다 | 23년 안내서 35~36쪽(PDF 50~51) |
| 허용 가능 수준은 가능한 낮게 설정하도록 지도한다 | 민간재해예방기관 매뉴얼 39쪽(PDF 45) |

따라서 AI 모델이 기준을 스스로 만들면 안 된다. 팀·전문가가 정한 기준표를 `criteria_version`으로 버전 관리하고, AI는 그 기준표를 RAG 문맥으로 받아 적용한다. 기준표가 없으면 `off`(`criteria_not_set`)로 둔다.

### 4.2 신호 4종과 안내서 대응표

| Safe-T 신호 (결정 1, 4쪽) | 사용자 행동 (4쪽) | 3단계 판단법 등급 | 허용 가능 여부 | 안내서의 개선 방법 | 근거 (문서·쪽) |
|---|---|---|---|---|---|
| 빨강 · 즉시 개선 | 대책 1개 이상 + 담당자 + 예정일 필수 | 상(빨강) "매우 높음" | 허용 불가능 | 즉시개선 | 쉽고 간편한 13쪽(PDF 17) 판단 기준 예시표, 26쪽(PDF 30) 개선 방법 표; 23년 51쪽(PDF 66) |
| 노랑 · 개선 필요 | 대책 1개 이상 + 담당자 + 예정일 필수 | 중(노랑) "보통" | 허용 불가능 | 가능한 빨리 개선 | 같은 표 |
| 초록 · 유지 관리 | 현재 상태 유지 또는 대책 추가 | 저(초록) "매우 낮음" | 허용 가능 | 현재 상태를 유지 / 필요에 따라 개선 | 같은 표. "추가 조치 없음" 또는 "현재 조치 유지"로 기록(쉽고 간편한 26쪽) |
| 꺼짐 · 판단 필요 | 저장 가능, 확정 불가 | 대응 없음 | 대응 없음 | 대응 없음 | **안내서 근거 없음.** 시스템 상태(AI 판단 불가)로 정의 |

확인한 대응 관계:

- 쉽고 간편한 안내서 13쪽 표는 상(빨강)·중(노랑)·저(초록)를 직접 쓴다. 표의 "허용 불가능" 칸은 상·중 두 행에, "허용 가능" 칸은 저 행에 걸쳐 있다(PDF 좌표로 셀 위치 확인).
- 같은 안내서 26쪽 표는 허용 불가능을 "즉시개선"과 "가능한 빨리 개선"으로, 허용 가능을 "현재 상태를 유지 / 필요에 따라 개선"으로 나눈다. 이는 Safe-T의 빨강·노랑·초록 행동과 초록의 `keep | add`(결정 7)에 그대로 맞는다.
- 다만 26쪽 표는 핵심요인 기술법(OPS) 절에 실린 표다. 3단계 판단법 절의 표와 함께 쓰는 것은 이 문서의 해석이다.

### 4.3 등급별 판단기준 후보 (안내서 예시, 채택 전)

| 등급 | 안내서 예시 판단기준 | 출처 | Safe-T 채택 |
|---|---|---|---|
| 상(빨강) | 사고 발생 시 사망 또는 장애가 남을 수 있는 위험 / 산업안전보건법에 따른 기준을 만족하지 못하는 경우 | 쉽고 간편한 13쪽(PDF 17) "판단 기준 예시" | **팀·전문가 결정 필요** |
| 중(노랑) | 사고 발생 시 요양이 필요한 위험 / 아차사고 사례가 있는 경우 | 같은 쪽 | **팀·전문가 결정 필요** |
| 저(초록) | 작업 수행에 영향을 미치지 않는 경미한 부상 또는 질병이 예상되는 경우 | 같은 쪽 | **팀·전문가 결정 필요** |

참고 예시(휴업 기간 기준):

- 민간재해예방기관 매뉴얼 39쪽(PDF 45)은 2·3·5단계 예시를 함께 보인다.
- 5단계 기준: 사망 또는 영구장애 / 6개월 이상 휴업 / 3일~6개월 휴업 / 3일 미만 휴업 / 휴업을 요하지 않는 부상·질병.
- 3단계(상·중·하)와 5단계 경계의 정확한 대응은 그림 배치로만 표시되어 있어 텍스트로 확정하지 못했다. 원문 그림 확인이 필요하다.

주의할 점:

- 민간재해예방기관 매뉴얼 51쪽(PDF 57)은 휴업이 필요한 부상 위험을 "중"으로 두고 "중"까지 허용하면 안전조치가 이뤄지지 않는다고 경고한다. Safe-T는 노랑도 대책 필수이므로 이 경고와 충돌하지 않는다.
- 위 예시의 "산업안전보건법 기준 미충족 → 상"은 법령 조항 검증 결과와 연결할 수 있다. 연결 여부와 방법은 팀·전문가 결정 필요다.

### 4.4 빈도·강도법을 쓸 경우

| 내용 | 근거 |
|---|---|
| 빈도(가능성)와 강도(중대성)를 곱셈·덧셈·행렬로 조합한다. 산출 기준은 사전에 정한다 | 23년 안내서 60~61쪽(PDF 75~76) |
| KRAS는 "5x4" 또는 "3x3" 척도를 제공한다. 현재 안전·보건 조치를 고려해 정한다 | 23년 61쪽(PDF 76), 쉽고 간편한 30쪽(PDF 34) |
| 예시 빈도: 빈번 3(1일 1회 정도)·가끔 2(1주 1회 정도)·거의 없음 1(3개월 1회 정도) | 23년 61쪽(PDF 76) "산출 예시" |
| 예시 강도: 대 3(사망·장애 발생)·중 2(휴업 필요)·소 1(비치료) | 같은 쪽 |
| 예시 허용 여부: 위험성 크기 4~9 허용 불가능(개선책 마련·이행), 1~3 허용 가능(필요시 개선) | 23년 62쪽(PDF 77) "결정 예시" |

- 이 예시는 **2개 등급**(허용 가능·불가능)만 나눈다. 허용 불가능 구간(4~9)을 빨강과 노랑으로 가르는 경계는 안내서에 없다. **팀·전문가 결정 필요.**
- 위 숫자는 모두 안내서의 "예시"다. Safe-T 기준으로 쓰려면 채택 결정이 필요하다.

### 4.5 체크리스트법을 쓸 경우

- 체크리스트법은 "적정"(허용 가능)과 "보완"(허용 불가능) 2개로 나눈다(23년 47쪽(PDF 62), 쉽고 간편한 19쪽(PDF 23), 소규모 사업장 안내서 11·13쪽(PDF 15·17)).
- 적정 → 초록, 보완 → 빨강 또는 노랑으로 대응할 수 있다. 보완 안에서 빨강·노랑을 가르는 근거는 없다. **팀·전문가 결정 필요.**
- `RAG용/음식점업 자율안전점검표.pdf`는 음식점 체크리스트 원천 후보다. 점검 항목과 신호 연결은 이번 범위에서 검토하지 않았다.

### 4.6 예상 신호와 조치 후 신호의 근거

| 내용 | 근거 |
|---|---|
| 감소대책 실행 후 위험성이 허용 가능 수준인지 확인해야 한다(고시 제12조 제2항) | 23년 96쪽(PDF 111) |
| 허용 가능 수준으로 내려오지 않으면 추가 대책을 세운다(제12조 제3항) | 같은 쪽 |
| 감소대책 시행 후 위험성 결정을 한 번 더 해야 한다 | 23년 98쪽(PDF 113) |
| 감소대책 순서: 제거·대체 → 공학적 → 관리적 → 개인보호구(제12조 제1항) | 23년 96쪽, 쉽고 간편한 27쪽(PDF 31) |
| 위험성 수준이 높은 것을 우선하고, 큰 사고 위험은 즉시 조치한다 | 23년 96쪽 |

- 조치 후 신호(F03)는 위 "대책 후 위험성 재결정"에 해당한다. 같은 기준표(`criteria_version`)로 판단해야 비교가 의미 있다.
- 예상 신호(S05-D)는 실행 전 추정이다. 안내서에 "계획 단계 예상 등급"을 따로 정하는 절차는 없다. 설계서 결정 5에 따른 Safe-T 기능이다.
- 추천 대책의 `control_type`은 제12조 순서를 따르는 제안 필드다. 추천 3개의 단계 구성(예: 공학적 1개 이상 포함)은 팀·전문가 결정 필요다.

## 5. 36쪽 확인 필요 항목 중 AI 관련 선택지

### 5.1 1번: 조치 후에도 빨강·노랑

현재 임시 처리: 조치 완료 + 후속업무에 '추가 개선' 항목 생성(36·40쪽).

| 선택지 | 내용 | 장점 | 단점 | AI 계약 영향 |
|---|---|---|---|---|
| A (현재안) | 완료 + '추가 개선' 새 항목 | 고시 제12조 제3항(허용 수준까지 추가 대책)과 맞음. 기록이 회차별로 남음 | 후속업무 건수가 줄지 않아 사용자가 끝나지 않는다고 느낄 수 있음 | `followup_needed=true`를 백엔드가 사용. 새 항목에 추천 대책 3개 생성 호출이 필요한지 결정 필요 |
| B | 완료만 두고 경고 표시 | 단순함. 결정 9와 충돌 없음 | 남은 위험이 후속업무에서 사라져 관리 누락 위험 | 응답 그대로 저장만 함 |
| C | 완료하지 않고 같은 항목을 다시 후속업무로 | 위험이 남은 상태를 정확히 표현 | 결정 9(결과 저장 = 완료)와 충돌 | 결정 9 변경 필요 |

근거: 23년 안내서 96쪽(PDF 111) 제12조 제2·3항. 이 문서는 A가 안내서 절차와 가장 가깝다고 본다. 최종 결정은 팀이 한다.

### 5.2 3번: 산정 실패 시 완료

현재 임시 처리: 완료 유지 + 신호 '판단 필요' + 재산정 버튼. 직접 선택 허용 여부는 미정.

| 선택지 | 내용 | 장점 | 단점 | AI 계약 영향 |
|---|---|---|---|---|
| A (현재안) | 완료 유지 + `post_signal=off` + 재산정만 | 결정 8(사용자 수정 불가) 유지 | AI가 계속 실패하면 off가 남음 | 재산정은 같은 F03 스키마 재호출 |
| B | A + 재시도 N회 실패 시 사용자 직접 선택 허용 | 막힘 해소 | 결정 8과 충돌. v3.11에서 "조치 후 위험수준 직접 선택"을 뺀 이력(36쪽) | `post_signal_source`에 `user` 추가 필요. 현재 스키마는 `ai`만 허용 |
| C | A + off가 남은 항목은 평가표 '조치 완료' 탭 이동 보류 | 미확인 위험이 완료로 보이지 않음 | 탭 규칙 추가 | 영향 없음(백엔드 규칙) |

기록 항목: 실패도 `judged_at`·`model_version`·`off_reason_code`를 남겨 원인을 추적한다.

### 5.3 5번: AI가 찾은 기기 저장 범위

현재 임시 처리: 이번 평가표에만 포함. 사업장 목록 자동 추가 여부는 미정. 데이터 구조는 34쪽 `assessment_equipment = 사업장 기기 스냅샷 + ai_found[] (equipment_id, detection_refs[], selected)`.

| 선택지 | 내용 | 장점 | 단점 | AI 계약 영향 |
|---|---|---|---|---|
| A (현재안) | 이번 평가표에만 | 오인식이 사업장 목록을 오염시키지 않음 | 다음 평가 때 다시 인식·체크 필요 | S04 요청의 `equipment[].origin=ai_found`로만 전달 |
| B | 사업장 목록에 자동 추가 | 다음 평가부터 편함 | 오인식 누적. 사용자가 모르게 사업장 정보 변경 | 인식 신뢰도·근거 사진 저장 필요 |
| C | 체크 후 "사업장 기기에도 추가" 확인을 따로 받음 | 사용자 확인 후 반영 | 화면 한 단계 추가 | A와 같음. 사업장 저장 API만 추가 |

AI 품질 관점에서는 오인식이 사업장 데이터로 번지지 않는 A 또는 C가 안전하다. 기기 인식 정확도는 아직 측정하지 않았다.

### 7.2 검증 결과 (2026-11-15, 로컬)

- 방법: Python `jsonschema`(Draft 2020-12)로 스키마 11개의 메타 스키마 검사, 예시 3개 검증, 경계 사례 22개 검사. 임시 환경(`uv run --with jsonschema`)에서 실행했고 프로젝트에 의존성을 추가하지 않았다.
- 결과: 메타 스키마 11개 통과. 예시 3개 유효. 경계 사례 22개 모두 기대대로 통과·거부.
- 거부를 확인한 경우: 빨강에 추천 2개, off에 원인 코드 없음, 빨강에 원인 코드 있음, 초안 응답에 사용자 필드(`current_measures`, `expected_signal`), 검증 안 된 법령, 알 수 없는 신호, 실패 응답에 결과 동봉, 입력 없는 S04 요청, 공백 키워드, 대책 없는 예상 신호 요청, 요청에 담당자 이름, F03의 `post_signal_source=user`.
- 미검증: `uri` 형식은 검사 라이브러리가 없어 확인하지 않았다. 실제 모델 응답으로는 검증하지 않았다. API 서버 구현은 범위 밖이다.
