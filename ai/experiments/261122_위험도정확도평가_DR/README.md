# 261122 위험도 정확도 평가 (DR)

작성일: 2026-11-22(Asia/Seoul). 작성: DR (Claude 보조 작성, 팀 검토 전).
기준 코드: `origin/main` `41302e7`(PR #47). 브랜치: `improve/risk-level-accuracy-261122`.

> 이 문서는 위험성 판단 기준을 새로 만들지 않는다. 팀 확정 문서의 표와 예시를 정답으로 옮겨 서비스 계산과 대조한다.
> 피해 수준(S)·핵심/보완 분류·등급표는 모두 서비스 판정 초안이다. **최종 위험도 판단은 담당 전문가가 한다.**

## 1. 목적과 결론

11/22 실모델 검증에서 모든 평가 행의 초기 신호가 `R`이었다. 이것이 계산 오류인지, 기준·입력 때문인지 확인한다.

- 계산 오류는 없었다. 팀 문서로 만든 정답 106건과 서비스 계산 경로 5개가 모두 일치했다.
- 11/22의 `R` 19행은 모두 입력 기반(`input_based`) 계약 v1의 기대값과 같다.
- `R`이 나온 원인은 기준과 입력 규칙이다. ① 입력 기반은 1.1 등급표를 쓴다. ② 입력에 조치 근거가 없으면 미충족으로 계산한다. ③ 사람이 현재 조치를 바꿀 수 없다.
- 공개 실제 평가 사례 8건은 척도 변환 기준이 없어 등급 정확도 계산에서 모두 제외했다.
- 서비스 계산 코드는 바꾸지 않았다. 정답셋 회귀 검사와 팀 결정 목록을 추가했다.

## 2. 현재 위험도 산출 규칙 (코드·문서 확인)

척도: 빈도(가능성) 입력은 없다. 카탈로그 시나리오의 **피해 수준 S1~S3**과 **기준 조치 충족 구간 C1~C3**으로 정한다.

- C1: 기준 조치 전체 충족. C2: 핵심 전부 충족, 보완 일부 미충족. C3: 핵심 일부 또는 전부 미충족.
- 모델은 등급·피해 수준을 만들지 않는다(`ai/assessment_authoring/tests/test_extraction.py`가 프롬프트에서 `severity`·`grade` 제외를 검사).

| 피해 수준 | FOOD-3LEVEL-1.2 (C3 / C2 / C1) | CATALOG-MVP-1.1 (C3 / C2 / C1) |
|---|---|---|
| S1 경미·응급처치 | 중 / 하 / 하 | 중 / 중 / 하 |
| S2 휴업 부상·질병 가능 | 중 / 중 / 하 | 상 / 중 / 중 |
| S3 사망·중상 가능 | 상 / 중 / 중 | 상 / 상 / 상 |

출처: `docs/implementation/risk-development-agreement.md`. 코드: `backend/domain/risk_policy.py`.

| 생성 모드 | 정책 | 생성 직후(초안) 신호 | 현재 위험도 | 예상 위험도 | 미평가(N) |
|---|---|---|---|---|---|
| 일반 평가표 `catalog_rls_v1` | 1.2 | 체크 0개로 계산. S1·S2는 Y, S3은 R | 체크한 현재 조치의 기준 조치 ID | 현재 ∪ 계획 ID. 생성 시에도 계산 | 시나리오 미연결 카드는 행을 만들지 않고 `unmatched`로 보존 |
| DB 기준 `catalog_v1`, AI 후보 `catalog_ai_v1` | 신규 1.2, 기존 1.1 | N | 현재 조치 목록 확인 + 현재 조치 선택 또는 '없음' 후 계산 | 확인 후 계획 체크 또는 '유지' 선택 시 계산 | 목록 확인 전, AI 추가 질문 미답변 |
| 입력 기반 `authoring_rag_v1` | 1.1 (`CATALOG-MVP-1.1-AUTO-1.0`) | 입력 근거로 바로 상/중/하 | 텍스트·전사에서 직접 인용한 `supported`만 충족. `unknown`·`not_effective`는 미충족. 사람이 수정 불가 | 계산하지 않음(`N`) | 없음 |

공통: 같은 조치 ID는 한 번만 센다. 직접 입력 대책·기준 ID 없는 추천은 저장하되 계산에서 뺀다. 계획은 현재 위험도를 낮추지 않는다.

## 6. 오차 원인 분석 — "모든 초기 신호 R"

| 원인 | 근거 | 영향 |
|---|---|---|
| 입력 기반이 1.1 표를 사용 | 1.1에서 S2·C3 = 상. 26개 시나리오 중 25개가 S2 이상 | 조치 근거가 없으면 26개 중 25개가 R |
| 조치 근거는 직접 인용 `supported`만 인정 | INTERFACES: unknown은 계산상 미충족 | 11/22 입력 3개 중 2개는 조치 언급 없음. 튀김 입력은 온도 제어 고장(핵심 미충족) |
| 사람이 현재 조치를 바꿀 수 없음 | `authoring_rag.protect_current` | 담당자 확인 뒤에도 R 유지 |
| 예상 위험도 미계산 | `assessment.save`가 입력 기반의 `after`를 건너뜀 | 개선대책을 골라도 예상은 N |

참고(적용하지 않은 대안): 같은 19행을 1.2 표로 계산하면 R 4 · Y 15다. 조치 근거 0개 초안 분포는 1.1이 R 25 · Y 1, 1.2가 R 12 · Y 14다.
행 자체가 틀린 경우(채소 손질 입력에 FRY 행, 튀김기 미사용 입력에 FRY 행)는 위험요인 선택 문제라 이 작업 범위가 아니다.

공개 사례 참고 대조(AI 보조 매핑, 정확도 지표에서 제외): 매핑한 5건은 모두 원문에서 대책 후 점수가 내려갔다. Safe-T 1.2로는 5건 모두 예상 신호가 R로 유지된다. 대책 하나로는 핵심 조치 전체를 충족하지 못하기 때문이다. 이 차이가 기준의 의도인지 전문가 확인이 필요하다.

## 8. 한계

- 정답셋은 팀 문서의 규칙을 옮긴 것이다. 현장 위험도의 정답이 아니며 전문가 평가와의 일치율은 측정하지 않았다.
- 11/22 재생의 조치 상태 라벨은 AI 보조이며 검수 전이다. 실제 모델의 `control_evidence`는 로그에 없어 확인하지 못했다.
- 공개 사례 매핑은 AI 보조 후보이며 검수 전이다.
- DB(MariaDB) 통합 테스트(`backend/tests`)는 로컬에서 실행하지 않았다. DB 없는 단위 검사만 실행했다.
- Cloud 실행·모델 재실행은 하지 않았다. 11/22 결과는 로컬 사본을 읽어 재생했다.
